# Jig: one UI protocol for agents and the people they work with

Status: **confirmed direction** by the product owner on 2026-10-15
(name, three uses, placement). Phases are planned one at a time. Epic
**E11 Jig**. A basic version is built inside **E10 Phase 3**
([`agent-runtime.md`](agent-runtime.md)). No tracker yet; E11 opens
`.cursor/workstreams/jig.md` when its first phase is planned. E10's part is
tracked in `.cursor/workstreams/agent-runtime.md`.

**Builds on** the earlier draft on branch `cursor/jig-design-c926`
(commit), which designed a jig as an agent-written app file in
the workspace. That draft's decisions are kept below, with amendments
marked. Its Mast postponement stands.

## What we are building

A **jig** is a small, declarative piece of UI made only from a closed
catalog of components. The VAM app draws it. Any data or side effect it needs
is one tool call through `vamd`, under Cedar. One protocol serves three
uses:

| Use | How it starts | What happens |
|---|---|---|
| **Ask** (human in the loop) | A playbook gate names a jig, or the agent calls `ask_user(jig, data)` | The task waits. The person's submit is the decision. `vamd` checks it against the result schema and resumes the task. |
| **Show** | The agent calls `show(jig, data)` | A card in the chat or side panel, live through queries. Nothing blocks. |
| **App** | A user opens an installed jig, or one the agent wrote to `ui/` | A standalone micro-app on the org's own tools and data |

Today's tool approval card and gate form become **built-in jigs**, so
there is one renderer and one set of rules for every interaction.

> A jig holds the work while the agent and the human finish it.

## Why

| User says | Today | Needs |
|---|---|---|
| "Pick the supplier" (2,000 of them) | The model lists them in prose, or a gate's `choices_from` dumps all of them | A searchable list that queries a tool as you type |
| "Order this product, quickly" | A chat back-and-forth, field by field | A form the model pre-fills and the person checks and submits |
| "Where's my PR?", "what's left?" | Prose, stale once written | A live status card, a todo list |
| "Approve this transfer" | Yes or no, context buried in chat | Details, selecting a subset, a reason |
| Builders: "we rebuild the same form for every agent" | No reuse | Components the community publishes and orgs install |

Human in the loop today is a tool approval card (Approve, Deny, Always)
and a playbook gate with a question and a flat `response_schema`.
`the VAM app/src/components/vam/playbooks/GateForm.tsx` renders text,
number, boolean, enum and enum-list fields only. Gates can take choices
from an earlier step (`choices_from`, `proto/vam/v1/workflow.proto:162`).

Chat is the wrong interface for structured input. HTML generated by a
model is unsafe. Weaker models are bad at producing consistent UI. A jig
fixes all three: the **model picks a jig and fills data, it does not
write UI**. That is the same rule as E10: move intelligence from the model
into the machine.

This adds one problem to `agent-experience.md`:

| # | Problem, as a customer would say it | Who feels it |
|---|---|---|
| **P14** | "Real work needs forms, pickers and status, not a chat transcript." | Anyone whose agent asks for structured input or reports structured state; builders who repeat UI per agent |

## Locked decisions

Do not re-litigate without editing this list. 1–10 come from the branch
draft; amendments are marked.

1. The artifact is a **jig**. One jig is one small piece of UI: a counter,
   an address form, a supplier picker, an approval.
2. The **primitive** catalog is `components.yaml`. VAM ships it. It lists
   each component, its props in order, the allowed action steps, and
   closed style tokens. No free CSS. **Amended:** agents never add to the
   catalog. **Composed components**, built only from primitives, are
   added by orgs and the community through release and review (§3).
   Primitives stay closed.
3. An agent may write `ui/<id>.jig` in the workspace (the App use). The
   text is a line language shaped like OpenUI Lang: one assignment per
   line. **Amended:** packaged jigs live in the catalog as
   `urn:vam:jig:<domain>/<ns>/<name>`, released and versioned like skills.
4. A **checker** turns a `.jig` file into a **jig IR** or a list of
   errors. The UI paints only the IR. A file that does not match the
   catalog is not rendered.
5. The renderer lives in the VAM app. It holds `$variables` and re-renders on
   change. **Amended (owner, 2026-10-27):** it paints the checked jig IR
   directly (our own small renderer over the standard form elements), not
   `@openuidev/react-lang`, which draws from OpenUI Lang text and would
   bypass decision 4. OpenUI Lang (agent-written `.jig` files, E11 Phase 4)
   and A2UI (§6) are input syntaxes that the checker converts into the IR.
6. `Query` and `Mutation` cross into VAM through the renderer's
   `toolProvider`. One call sends the current fields; one result comes
   back. Success applies it. Failure leaves the fields unchanged and skips
   later `@Run` steps.
7. Typing stays in the page. Only a select a query depends on, or a button
   that runs a mutation or a submit, reaches VAM.
8. A model fill is a tool that calls the inference broker with a fixed
   task and returns a field object. `@ToAssistant` is not in the catalog.
   A click never sends a chat message.
9. `@Set` runs in the renderer. A runtime crate for transitions that must
   not be trusted to the page is a later decision (§8, Phase 7).
10. No second form library next to the renderer.
11. **New: one protocol, three uses** (Ask, Show, App). The approval card
    and the gate form are built-in jigs.
12. **New: a click is the person acting.** A `Mutation` clicked in a jig
    runs as the viewing user, on behalf of the agent. Cedar evaluates the
    user as principal with the agent and task as context, and audit and
    the effect journal record it as a human action.
13. **New: a jig never exceeds the agent.** The tools a jig may call are
    what its package declares, intersected with the agent's permissions
    and the user's.
14. **New: `vamd` validates every submit** against the result schema,
    and a selection may only contain items that were offered (as playbook
    gates do today). The app is never trusted for the result. A `submit`
    result is the union of the button action's `set` names (literals) and
    `with` names (state values), so `vam.approve` carries `decision` from
    `set`.
15. **New: the jig IR is our format.** A2UI interoperability is an
    adapter, not the primary format (§6).

## 1. The protocol

### 1.1 Parts

| Part | What it is | Where it lives |
|---|---|---|
| Primitive | A component in `components.yaml` | Shipped with the VAM app; mirrored for agents |
| Composed component | A named tree of primitives with typed props, e.g. `SupplierPicker` | A jig package |
| Jig | A root tree, state, queries, mutations, result schema | `.jig` source; checker → IR |
| Jig package | One or more jigs and components, a manifest, capability declarations | The catalog, `urn:vam:jig:…`, versioned |
| Interaction | One instance of a jig shown to someone: jig ref, data, use, target | Created by `vamd`, stored on the task |

### 1.2 The jig file

From the branch draft, unchanged in shape. State is `$name = default`.
Actions are `@Set`, `@Reset`, `@Run`, and **new** `@Submit`, which ends
an Ask interaction with the current values as the result.

Supplier picker for a purchase-requisition gate:

```text
$q = ""
$supplier = ""
$qty = 1
found = Query("erp.search_suppliers", {query: $q}, {items: []})
search = Input("Search suppliers", $q)
pick = List(found.items, $supplier, "id", "name")
qty = NumberInput("Quantity", $qty)
send = Button("Create requisition", Action([@Submit({supplier: $supplier, qty: $qty})]))
root = Stack([search, pick, qty, send])
```

The other fixtures from the branch draft (counter, shipping address, open
a pull request) stay as the spec for Phases 1 and 2.

### 1.3 The package manifest

```yaml
id: urn:vam:jig:local.vam.dev/acme/purchase-requisition
version: 1.2.0
jigs:
  - name: create_requisition
    source: jigs/create_requisition.jig
    input_schema:  {…}   # data the agent or gate binds in
    result_schema: {…}   # what @Submit must produce
components:
  - name: SupplierPicker
    source: components/supplier_picker.jig
tools:                   # the only tools any jig here may call
  - erp.search_suppliers   # query
  - erp.create_supplier    # mutation
```

Publishing checks every `.jig` against the catalog and every tool against
the manifest. Install shows the tools as the package's capability
request, the same consent flow as skills.

### 1.4 An interaction

| Field | Meaning |
|---|---|
| `jig` | A pinned package ref and jig name, or a workspace path (App use) |
| `use` | `ask`, `show` or `app` |
| `data` | Values bound into the jig, checked against `input_schema`. Untrusted strings are shown as text only. |
| `bindings` | For gates: `steps.<id>.output.<path>` mapped to inputs (extends `choices_from`) |
| `audience` | Who may act: the task owner, a named approver, or a role (gates today) |
| `deadline` | For Ask: the wait's deadline and `on_timeout` (E10 waits) |

Lifecycle of an Ask: `vamd` creates the interaction → the task enters
`waiting(input)` and may park → the app (later Slack) shows it → queries
and mutations run as the person (decision 12) → `@Submit` sends the result
→ `vamd` validates it (decision 14) → the result goes to the task's inbox
→ the task resumes.

### 1.5 Where interactions come from

| Source | How |
|---|---|
| Playbook gate | `PlaybookStep.form_ref` (new field) names a jig; `bindings` fill it. A gate with only `response_schema` gets a **generated default jig**, so existing playbooks keep working. |
| Tool approval | The built-in `vam.approve` jig (Approve, Deny, Always, Always deny, details). A tool may name a richer approval jig in its manifest. |
| Playbook start | The built-in ask card from E10 Phase 0 (`agent-runtime.md` §IV.3a), with the playbook's input form |
| Agent | `ask_user(jig, data)` and `show(jig, data)` tools. The agent picks from jigs attached to it, ranked like tools. |
| User | Opens an installed jig, or a `ui/*.jig` file the agent wrote |

## 2. Four levels

| Level | Example | Made by |
|---|---|---|
| Primitives | Stack, Text, Input, NumberInput, Select, List, Table, Badge, Button | VAM, closed |
| Components | SupplierPicker, PrStatus, TodoList, DiffView | Orgs and community, from primitives only |
| Jigs | Create purchase requisition, Review PR, Approve transfer | Orgs and community |
| Journeys | A playbook whose gates use jigs | Agent authors |

A jig package plus the skill, MCP connection or HSP broker behind its
tools, plus a playbook, is a **micro-app** an org installs and runs on
its own systems under its own Cedar rules: publishers build once, orgs
install and govern.

## 3. Security

- **Closed rendering.** Only catalog primitives; no HTML, CSS or script;
  no `@OpenUrl`, no `@ToAssistant`. Text in data is never interpreted.
- **Decision 12:** clicks are human actions, authorized as the user.
- **Decision 13:** a jig's tools are its declared list ∩ the agent's
  permissions ∩ the user's.
- **Decision 14:** `vamd` validates every result; selections are limited
  to offered items.
- **Rate limits** per interaction on queries (search-as-you-type),
  debounced in the renderer and enforced in `vamd`.
- **Supply chain:** packages are checked at publish, consented at install,
  and signed before the public marketplace (E6, P9).
- **Injection:** an agent asked by untrusted content to open an Ask that
  runs a mutation still needs the person to click; the mutation runs as
  that person under Cedar.

## 4. Built for any model

The model never writes UI in the Ask and Show uses. It chooses a jig by
name (ranked, with a `when` line like playbooks) and fills `data` that is
schema-checked before anything renders. A bad fill is returned to the
model as a schema error (E10 call repair). Writing jigs (the App use) is
for builders and stronger models, and the checker gates it.

## 5. Surfaces

The app draws every jig first. Through `vam.notify` (E5) a jig can render
in Slack or email when every component has a mapping there, and falls
back to a link into the app when not. Mast (public web) stays postponed.

## 6. Interoperability (secondary)

- **A2UI** (Google's declarative agent-UI format) uses the same model: a
  catalog of approved components drawn natively. An adapter can import
  A2UI payloads from other agents into jig IR when every component maps,
  and export jigs as A2UI for other clients. Not the primary format.
- **MCP Apps** (`ui://` resources, HTML in a sandboxed frame) can show a
  vendor's own UI from a connected MCP server. That is a lower-trust tier
  outside the closed catalog, behind a sandbox and an explicit
  per-connection allow.

## 7. Placement

**Basic version in E10 Phase 3.** Phase 3 has to build chat cards anyway
(progress, questions, the playbook ask card), so they are built once, on
the jig renderer:

- The catalog and IR on paper, the checker, and the renderer in the VAM app
  (branch Phases 0–1).
- Built-in jigs: `vam.approve`, `vam.question`, `vam.progress`,
  `vam.playbook_start`, and the generated default for `response_schema`
  gates.
- `show(jig, data)` and `ask_user(jig, data)` with built-in jigs only.
  No queries or mutations yet.

2. The first primitive list beyond the branch's six: `List`, `Table`,
   `NumberInput`, `Badge` are proposed here. Which are in the E10 Phase 3

3. Is `components.yaml` also seeded into the workspace for agents to read?
   Branch question 2.

   Spaces?
5. Can a Show card's queries keep running after the task ends, or only
   while the task lives?

## What we are not building

- Mast, public websites, anonymous visitors.
- Free-form HTML, CSS or script from agents or packages.
- A catalog agents can extend.
- Sending every keystroke into the guest.
- A second form library.
